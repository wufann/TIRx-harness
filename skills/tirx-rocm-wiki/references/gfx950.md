# gfx950 (CDNA4: MI350X / MI355X) facts for kernel authors

## Machine

- MI355X: 256 CUs (8 XCDs x 32), 4 SIMDs per CU, wave64. Workgroup up to 1024 threads.
- LDS: 160 KB per CU, usable by one workgroup. Global -> LDS DMA (`global_load_lds`,
  `buffer_load ... lds`) writes LDS without passing through VGPRs.
- Registers per SIMD lane: 512 VGPRs split between ArchVGPRs (v) and AccVGPRs (a, "AGPRs").
  MFMA can read C from and write D to AGPRs; other VALU ops cannot use AGPRs directly
  (`v_accvgpr_read/write` move them). With 256 accumulator floats per lane (a 128x128
  wave tile of 16x16 MFMAs) the accumulators must live in AGPRs.
- Caches: 4 MB L2 per XCD, 256 MB Infinity Cache (MALL) shared. Workgroups are
  dispatched round-robin across XCDs; neighbouring workgroup ids do not share an L2.
- Peak dense: bf16 / f16 about 2.5 PFLOPS, fp8 about 5, MXFP4 about 10 (16x16x128 f8f6f4
  with FP4 operands issues in 16 cycles, 4x the FLOPs of a 16-cycle 16x16x32 bf16 MFMA).
  At 2.4 GHz one CU retires one 16x16x32 bf16 MFMA per SIMD every 16 cycles.

## MFMA operand layouts (lane l = 0..63, verified against torch)

A is row-major M x K, B is given as Bt = N x K (K contiguous), D = M x N.

| Instruction | A per lane | Bt per lane | D per lane |
|---|---|---|---|
| 16x16x32 bf16 / f16 | row l%16, k (l//16)*8 .. +8 | col l%16, same k | col l%16, rows (l//16)*4 .. +4 (`float32x4`) |
| 32x32x16 bf16 / f16 | row l%32, k (l//32)*8 .. +8 | col l%32, same k | element i: col l%32, row (i//4)*8 + (l//32)*4 + i%4 (`float32x16`) |
| 16x16x128 f8f6f4 (FP4) | row l%16, k (l//16)*32 .. +32 as `int32x4`; byte j holds elements 2j (low nibble) and 2j+1 | col l%16, same k | as 16x16x32 |

- A and Bt fragments are each one 16-byte `ds_read_b128` from K-contiguous LDS rows.
- Swapping the roles of A and Bt computes D^T: a lane then holds 4 consecutive columns
  of one row, which allows one 8-byte (bf16) or 16-byte (f32) store per tile.
- Scaled MFMA: each lane supplies one E8M0 scale byte per operand for its 32-element K
  block (A: row l%16, block l//16), selected from a 32-bit register by `opsel`
  (byte b -> `op_sel = b & 1`, `op_sel_hi = b >> 1` in the asm encoding).
  Value = e2m1 * 2^(scale - 127). e2m1 codes: 0, 0.5, 1, 1.5, 2, 3, 4, 6; bit 3 = sign.
- MFMA results are not available to non-MFMA consumers for several cycles; LLVM inserts
  the required `s_nop` for intrinsics, not for inline asm.

## Counters and waits

- `vmcnt`: outstanding vector-memory loads (including DMA into LDS), up to 63.
- `lgkmcnt`: outstanding LDS, GDS, constant (scalar memory) and message ops, up to 15.
  LDS ops complete in order; scalar loads can return out of order.
- A wave that consumes data loaded by *other* waves needs both its own wait and an
  `s_barrier`: wait for your DMAs (`vmcnt`), then barrier so everyone's have landed.
- Ring pipelines count stages with vmcnt: with S stages in flight and D DMAs per stage,
  stage k is ready after `s_waitcnt vmcnt((S-1-k) * D)` + `s_barrier` (aiter's
  `vmcnt(8)` / `vmcnt(12)`).
- Before overwriting an LDS buffer with DMA, every wave must have finished reading it:
  a barrier between the last `ds_read` of the old contents and the new DMA issue.

## LDS

- LDS is banked (4-byte banks); a 16-byte-per-lane access (`ds_read_b128`) is serviced
  in lane groups. Tiles with 128-byte rows read as MFMA fragments conflict unless the
  16-byte chunk index is XOR-swizzled with the row: storing global chunk c of row r at
  chunk `c ^ (r % 8)` measured zero `SQ_LDS_BANK_CONFLICT` in the BF16 GEMM. Check the
  CDNA4 ISA guide's LDS chapter for the exact bank model before designing a new layout.
- `ds_read_b64_tr_b16` reads a transposed 4 x 16-bit fragment (gfx950).

## Buffer resources

A buffer resource (V#) is 128 bits in 4 SGPRs: base, stride, num_records, flags.
`buffer_load_lds` builds it from `base` / `num_records`; addressing is
`base + voffset (per lane, 32-bit) + soffset (uniform) + offset (immediate)`, and
out-of-range accesses return 0. Moving the per-iteration advance into `soffset` keeps
the per-lane `voffset` loop-invariant and removes VALU address math from the loop.
